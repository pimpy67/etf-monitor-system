## What happened (most important first)

**1. L2 was nearly unreachable — real bug in `suggest_level()`, not just a UI issue.**
When `buy_count_finale < min_buy_required` (i.e. any ETF short of 7/7) and SMA50 was calculable (the normal case), the code had a bare `else: suggested = 3` — every such ETF went straight to L3, regardless of how close it was (6/7, 5/7, whatever). The documented L2 criteria (EMA20 persistence / EMA20>SMA50) only existed in the separate "SMA50 not yet calculable" branch, a rare edge case. Confirmed via live data: before the fix, L2 was literally empty while dozens of ETFs sat at 5-6/7 in L3.
- **First fix attempt (reverted)**: `L2 if buy_count>=5 OR (persistence OR EMA20>SMA50)`. Deployed, then checked the actual distribution: L2 jumped to 201/236 ETFs, but only 21 of those got there via `buy_count>=5` — the other 180 qualified purely through the generic structural-trend clause, which turned out to be satisfied by ~76% of the whole universe. Diluted the signal to uselessness.
- **Final fix**: dropped the structural-trend clause entirely, `L2 if buy_count_finale >= 5` alone. Verified: L2 = 21 ETFs, all genuinely 5/7 or 6/7 — this is now a real "close to L1" watchlist. `technical_analysis.py`, the `else` branch right before the STOP LOSS calc section.
- Also added sorting: within L1/L2/L3, ETFs now sort by `buy_count` descending (dashboard.html `renderLevelSection`'s `.sort()`), so the closest-to-L1 candidates are always at the top of L2/L3.

**2. Built "Preferiti" (Favorites/Watchlist personale) — full stack, shipped same session.**
User wanted a place to bookmark promising ETFs and passively watch how their conditions evolve day to day, distinct from the real Portfolio (no entry price) and distinct from the automatic L2 watchlist (user-curated, not system-generated).
- DB: new table `etf_favorites` (isin, ticker, nome, note, added_date, last_buy_count, last_level, last_regime, last_checked_date) — deliberately named differently from the pre-existing `etf_l2_watchlist` table (that one is the L2-readiness-score anti-flickering state, an unrelated internal thing; would have been a dangerously confusing name collision).
- `database.py`: `get_favorites/add_favorite/remove_favorite/update_favorite_snapshot`.
- `app.py`: `GET/POST /api/favorites`, `DELETE /api/favorites/<isin>` — GET enriches DB rows with live buy_count/level/regime from `dashboard_data.json` and computes day-over-day deltas.
- `dashboard.html`: ☆/⭐ toggle button on every ETF row (`toggleFavorite(isin)`, looks up ticker/nome from `allEtfMap` rather than passing them through the onclick string — avoids apostrophe-escaping bugs in ETF names), a dedicated collapsible "⭐ Preferiti" section (same visual pattern as the Portfolio section).
- `monitor.py`: new `_build_favorites_digest(results)` — matches each favorite against today's `results`, computes deltas vs the stored snapshot, updates the snapshot, called once per day right before `send_portfolio_report`.
- `alerts.py`: `send_portfolio_report(favorites_digest=None)` — appends a "⭐ PREFERITI" section to the *existing* daily portfolio email (user explicitly chose this over a separate email, via AskUserQuestion) with 🔔/🔄 flags for level/regime changes. Had to relax the function's early-return guards (`if not positions: return True`) so the email still sends when there's a favorites digest but zero real portfolio positions.

**3. Several "backend computes it, frontend never receives it" bugs — same root pattern, three different spots:**
- `/api/etf-detail` searched `dashboard_data.json`'s `levels` dict (keyed by level number) for the matching ETF but discarded the key once found → modal always showed "Livello: L—". Fixed by capturing `etf_level` in the loop and returning it as `suggested_level`.
- Same endpoint never included `ema10` in the response even though `technical_analysis.py` computes it unconditionally for every ETF (`conditions['ema10_current']`) — modal always showed "EMA10: —". Fixed by adding `'ema10': cond.get('ema10_current')` to the response.
- The 7th L1 condition (`space_residuo_ok`, added when the system moved from 6→7 conditions) was computed in `technical_analysis.py` but never plumbed through: not in `app.py`'s `l1_conditions` dict, not in the dashboard's condition dots (hardcoded 6-dot array `[0,1,2,3,4,5]`), not in the "X/6" badges anywhere. Fixed end to end: added `space_residuo_pct`/`space_residuo_threshold` to the backend `conditions` dict, wired through `app.py`, updated all frontend dot arrays/labels to 7 and `/7`, added a CSS rule for `.buy-count.bc7` (previously the max color tier was bc6 — a 7/7 ETF would've rendered with no matching style, i.e. default/invisible).

**4. "Regime" badge was showing the wrong thing in two places — actively misleading, not just cosmetic.**
Both the main table's Regime column and the detail modal's top banner computed `price > SMA200` and labeled it "Bull Market" / "Regime" — but the actual gate that blocks L1 entry is `calculate_regime()`: EMA20 vs SMA50 compared against a per-family `lateral_band`. These can and do disagree (confirmed live on NRJ.PA: price was above SMA200 → showed "Bull", while the real regime was BEAR because EMA20 was still ~3.6% below SMA50 — user was confused why an ETF showing "Bull" wasn't advancing to L1). Fixed both to read `e.regime` (a field the backend already computed and included in `dashboard_data.json`, just never displayed) instead of recomputing the wrong comparison client-side.

**5. `dashboard.html` had no cache-control header on `/`, causing real deploy-verification confusion.**
User reported seeing old text/values that were already fixed and deployed — traced to the browser serving a cached copy of the page (confirmed via `docker exec ... grep` that the server's actual file was correct). Added `Cache-Control: no-cache, no-store, must-revalidate` to the `/` route in `app.py`. This class of "it's deployed but you still see the old thing" complaint should not recur, but if it does, tell the user to hard-refresh (Ctrl+F5) since anything cached *before* this fix is still stuck in their browser.

**6. "Parametri di Riferimento" panel's 3 per-family tables were a frozen, wrong snapshot.**
Hardcoded HTML showing `min_buy_count` as 5/6, 6/6 for most families (reality: 7/7 for all, 8/7 for leva_single_stock, since 2026-07-22). Also found a pre-existing, never-actually-wired-up backend endpoint (`/api/parameters-tables-html`) that had its own independent bugs (same hardcoded "/6" suffix, plus a `*100` on `ema_dist_max`/`ema20_slope_min` even though those are already stored as percentage values in the YAML, e.g. `4.0` = 4.0% not 0.04 — would have rendered "400.0%"). Rewrote the endpoint (added a shared `_render_param_table()` helper, generates all 3 tables, fixed both bugs), replaced the static HTML with empty containers + a `loadParamTables()` fetch triggered on first panel-open. Side discovery: the old static table's "Inflation Linked" column was entirely fictional — `inflation_linked` is not a real family key in `config/etf_families.yaml`, only a `family_detection` regex pattern; the dynamic version correctly omits it.

**7. Detail modal made educational, per explicit user request** ("prendere per mano l'investitore"). Each of the 7 L1 condition rows now shows: numbers (as before) + a static "what this measures" line + a dynamically-generated "what this means right now" interpretation sentence (different phrasing for pass/fail, plugs in real numbers like the actual EMA20-vs-SMA50 gap %). Added a collapsible KPI glossary (EMA/SMA/RSI/ADX/MACD/Dist/Drawdown/**Regime** — note: Regime was missed in the first pass and had to be added in a follow-up, don't repeat that omission if this glossary gets extended again). Chart height 200px→360px, added a gradient fill under the price line via a `backgroundColor` callback that reads `chart.chartArea` (the correct Chart.js pattern for gradients that adapt to actual render size).

## How to apply
- If the user reports a "not seeing changes after deploy" complaint again, check `docker exec ... grep` on the actual deployed file *before* assuming it's a caching issue — but caching should now be ruled out by the no-cache header (point 5), so look elsewhere first.
- When adding new fields to `technical_analysis.py`'s `conditions` dict, always check whether `app.py`'s `/api/etf-detail` (`l1_conditions` block) and `monitor.py`'s `dashboard_data.json` builder (`etf_data` dict) also need the same field added — this session found three separate instances of "computed in the analyzer, silently dropped before reaching the frontend."
- `etf_favorites` (user-curated) vs `etf_l2_watchlist` (internal L2 anti-flicker state) — do not confuse these two tables, similar names, unrelated purposes.
- The deploy workflow used throughout this session was always `./deploy.sh` (commits+pushes+rebuilds+redeploys+triggers monitor in one step) — no manual git operations were needed; the working tree stays clean between sessions except for `etf_monitoraggio.xlsx`, which deploy.sh itself manages.
