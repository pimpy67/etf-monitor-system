**Trigger**: user asked why PHAG (WisdomTree Physical Silver, JE00B1VS3333, L0) was missing from the daily portfolio email. Investigation found it had been auto-closed in the DB (`status='exited'`, exit_rule='TP raggiunto') — but the user confirmed via a pasted Directa screenshot they still held all 48 shares. See [[etf-no-auto-exit-real-positions]] for the standing rule this established.

**Fixes shipped and deployed (all live in production, commits on same day)**:
1. Removed the automatic `status='exited'` write in both `monitor.py::_update_portfolio_l0_suggerito` and `_update_portfolio_l1_suggerito` — SL/TP hit is now log/alert-only (`🟢 TARGET RAGGIUNTO`/`🔴 SL RAGGIUNTO`), position stays `active`.
2. `order_pricing.py`: removed the `tp_suggerito > current_price` guard on the TP-proximity ratchet — it used to stop tightening once price passed the target (harmless before, since the old code force-closed right there; now the position can stay open past target so the Stop must keep tightening).
3. **ATR-based per-instrument volatility override** (`WIDE_TIER_ATR_PCT = 2.0` in `order_pricing.py`, new `atr_pct` param on `compute_order_prices`): the existing wide-tier buffer (1.5%/2.0% instead of 1%/1.5% distance) was gated on family-level `sl_initial_pct >= 7%`. PHAG's family `oro_metalli_preziosi` groups Gold and Silver under one `sl_initial_pct=5%` — under the cutoff, even though Silver's real measured ATR14 was 2.87% (vs the family's "moderate" profile) and its actual daily range (20-day sample) averaged 2.28%, several days 3-5%. A 1% stop buffer was inside normal daily noise for this instrument specifically. Fix computes real ATR14 from `db.get_ohlc_by_isin()` per position in both L0/L1 update functions and passes it to `compute_order_prices`; when available it overrides the family-level proxy. Verified end-to-end: user had manually widened their real Directa Stop from 53.57/53.03 to 53.30/52.77 based on this reasoning before the code fix landed — after deploy the system computed the identical 53.2983/52.7654 on its own. **Gotcha discovered mid-fix**: the tightening ratchet never loosens (`floor = max(today's candidate, previous_persisted)`), so the stale pre-fix tight value (53.5689, persisted in `tp_proximity_stop_max`) kept winning over the new correct wider value even after deploying the ATR fix — had to manually `UPDATE ... SET tp_proximity_stop_max=NULL` for PHAG to let the ratchet restart from the corrected number. Any future "I fixed the buffer logic but the position still shows the old tight stop" symptom on an existing open position needs the same manual reset.
4. PHAG reactivated (`status='active'`, `exit_date/exit_price/exit_rule` cleared) — confirmed real position, not touched otherwise.
5. **ISIN + clickable dashboard link added to every ETF email** (`alerts.py`): daily portfolio report (L1, L0, Preferiti, Radar L2 — done first), then on explicit follow-up request also `send_new_entries` (new L1/L0), `send_l1_exit`, `send_portfolio_signals`, `send_tp_proximity_alert`, `send_shadow_entries`. Link format: `https://etf.andreapavan.tech/?isin={isin}&ticker={ticker}`. `send_portfolio_l1_sync_alert` was checked and skipped — confirmed dead code, never called anywhere.
6. Dashboard side (`dashboard.html`): added a `?isin=&ticker=` query-param handler on `DOMContentLoaded` that calls the existing `openETFDetail(ticker, isin)` after `loadData()` resolves, auto-opening the detail modal for deep-linked ETFs.
7. Added a disclaimer paragraph to the Shadow Monitor email (`send_shadow_entries`) after a user follow-up question about why a shadow "Candidate Model B" entry (LGQM.DE, `mercati_emergenti`) showed only 5/7 when clicked through to the dashboard — expected behavior, not a bug: the dashboard link always shows **native** parameters (7/7 gate, family `mm200_distance_max`), while the Shadow Monitor uses looser experimental Candidate Model B params (`mm200_distance_max=7.0%` flat, `adx_entry-4`, 6/7-with-MACD-mandatory gate) documented in `CLAUDE.md` under CANDIDATE_MODEL_B_20260807. The email now says this explicitly so it's not confusing every time.

**Not yet done / consider next time**: the same "grep for auto status-changing" audit from [[etf-no-auto-exit-real-positions]] hasn't been run over `shadow_monitor.py`/`shadow_monitor_l0.py` — those are *supposed* to auto-track (hypothetical, not real money), so no action needed there, just noting it was consciously out of scope, not overlooked.
